# crontab-linter

A small command-line tool that checks cron schedule expressions and reports
problems with the line number they occurred on.

## Why

Cron expressions look trivial but have a handful of sharp edges that are easy
to get wrong and painful to notice, because the failure mode is "the job
silently never runs" rather than an error at write time:

- `60 * * * *` looks like a typo for `0 * * * *` but cron tools disagree on
  whether they reject it or just silently misfire.
- `0 0 1 * 1` (midnight, the 1st of the month, and every Monday) does not
  mean "run only when both match" - most cron implementations run the job
  when *either* field matches, which is rarely what the author intended.
- `0` and `7` both mean Sunday in the day-of-week field; mixing them with a
  range like `5-7` produces a schedule that's easy to misread.
- Macros like `@reboot` and `@daily` are only valid if spelled exactly
  right; `@fortnightly` will be silently ignored by most cron daemons.

`cronlint` catches these by parsing each of the five schedule fields
(minute, hour, day of month, month, day of week), checking values and
ranges against their valid bounds, and flagging the day-of-month /
day-of-week interaction as a warning.

## Usage

```
$ cat crontab
# nightly backup
0 2 * * * /usr/local/bin/backup.sh

# oops: 60 isn't a valid minute, and Saturday is spelled wrong
60 3 * * SAT /usr/local/bin/broken.sh

$ cronlint crontab
crontab:5: error: minute field "60": "60" is not a valid minute
crontab:5: error: day of week field "SAT": "SAT" is not a valid day of week
```

With no arguments, `cronlint` reads from stdin, so it fits into a pipeline:

```
$ crontab -l | cronlint
```

Each finding is printed as `source:line: severity: message`. The exit code
is 1 if any line produced an error-level finding, 0 otherwise (warnings
alone don't fail the run).

Some schedulers (Quartz-derived tools, several Node and Python cron
libraries) use a 6-field dialect with a leading seconds field. Pass
`-seconds` to check files in that dialect instead of standard 5-field cron:

```
$ cronlint -seconds crontab
```

There's no reliable way to tell the two dialects apart automatically - a
5-field line with a one-word command has the same field count as a bare
6-field schedule - so `cronlint` has to be told which one it's reading.

Pass `-json` to print each finding as one JSON object per line instead of
the plain-text format, for feeding into other tools:

```
$ cronlint -json crontab
{"file":"crontab","line":5,"severity":"error","message":"minute field \"60\": \"60\" is not a valid minute"}
{"file":"crontab","line":5,"severity":"error","message":"day of week field \"SAT\": \"SAT\" is not a valid day of week"}
```

## Streaming input

`cronlint` reads its input one line at a time with `bufio.Scanner` instead
of buffering the whole file. Memory use is bounded by the longest single
line, not by the size of the input, so it can check a crontab-style file
generated by config management that runs to tens of thousands of lines
without the process's memory footprint growing with it.

## What it checks today

- field count (5 schedule fields expected by default, 6 with `-seconds`,
  plus an optional command)
- each field's values and ranges against their valid bounds
- step values (the `/n` part of `*/15`) being a positive integer
- unknown `@` macros
- day-of-month and day-of-week both being restricted at once (warning)
- the vixie-cron/Quartz extensions `L` and `W` in the day-of-month field
  (`L` for last day of the month, `15W` for the nearest weekday to the
  15th, `LW` for the last weekday of the month), and `L` and `#` in the
  day-of-week field (`5L` for the last Friday of the month, `MON#2` for
  the second Monday)

Blank lines, `#` comments, and `NAME=value` environment assignments are
recognized and skipped, matching real crontab syntax.

## What it doesn't check yet

- duplicate or overlapping values within a single field
